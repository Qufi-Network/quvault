# The portable wallet invariant

**Design note. Nothing here is implemented, and none of it may be implemented in Phase 1.**

---

## The invariant

> **The wallet is portable across compatible scanners. A person's palm must not open a
> different wallet merely because a different scanner was used.**

A scanner is a sensor. It is not a key, not a key holder, and not a factor in deciding which
wallet exists. If replacing a broken scanner with a compatible one would change the address a
palm opens, the design is wrong and the money is gone.

Two consequences follow immediately, and both are already true of the code as it stands:

- Nothing in [src/scanner.js](src/scanner.js) returns, accepts, wraps or derives key material,
  and `assertProvider` refuses a provider that offers to.
- [client/wallet.js](client/wallet.js) does not import the scanner module at all, so no wallet
  operation can take a scanner as an input. There is a test that asserts this.

## The correction this note makes

The Phase 0 audit sketched a target where the wallet key came from
`KDF(phrase-derived secret, palm-derived secret)`. **That was wrong and is superseded by this
note.** Deriving the spending key from the palm makes the key as fragile as the biometric: a
re-enrollment, a healed cut or a firmware change moves the key, and the coins are unreachable.

The palm belongs one layer up, as a **key-encryption capability** — something that unlocks an
independently generated key, never something the key is made of.

## The intended architecture

```
  NIR palm capture
        │
        ▼
  quality gate + PAD                   ── on the device
        │
        ▼
  biometric feature extraction         ── on the device
        │
        ▼
  fuzzy extractor / stable secret      ── tolerates a bounded error rate
  reconstruction                          and reproduces one stable secret
        │
        ▼
  palm-derived key-encryption          ── a KEK. It wraps and unwraps.
  capability                              It is not the wallet key.
        │
        ▼
  decrypt / unwrap access to the ─────────► WALLET PRIVATE KEY
  wallet key                                generated by a genuine CSPRNG,
                                            independently of any biometric
```

**The wallet private key is generated by a CSPRNG and by nothing else.** It is not derived
from the palm, not seeded by the palm, and not influenced by the palm. The palm decides
whether the existing key can be unwrapped; it never decides what the key is.

## How this maps onto the code that exists today

The shape is already in place, which is why this is an extension rather than a rewrite:

| Today | Under this design |
|---|---|
| Key generated in the browser: CSPRNG + server randomness + ceremony jitter → HKDF → BIP39 | unchanged — this is already a genuine CSPRNG-generated key |
| Encrypted at rest under `HKDF(unlockSecret, salt, 'quvault device key v1')` | unchanged in shape |
| `unlockSecret` released by the server only after palm approvals complete | joined by, or replaced with, a palm-derived KEK reconstructed on the device |

The unlock secret is already a key-encryption capability gated by a palm decision. What
changes is where that capability comes from — a server release today, a fuzzy extractor on the
device later — not what it does.

## What must be measured before any of this ships

Three numbers, measured on real hardware and a real population. None of them exists:

1. **False rejection rate** at the operating threshold — how often a legitimate owner is
   locked out of their own money.
2. **Error-correction budget** — and what happens to someone whose palm drifts past it.
3. **Entropy of the extracted representation** — measured, not asserted.

Until those exist:

- **No claim may be made about biometric key strength anywhere in this product.** The palm
  image is not "sufficient entropy" and nothing may say that it is.
- **The recovery phrase must remain a complete and sufficient recovery path on its own.** If a
  palm-derived capability is added, losing it must never lose the money — otherwise the fuzzy
  extractor's failure rate becomes a fund-loss rate.

## Portability versus binding

"Any compatible scanner works" and "this exact device attested" cannot both hold. The trust
anchor is therefore a **class** of device — a manufacturer key covering a model and firmware
range — with the accepted consequence that a compromised device in that class compromises the
class, and revocation is by class rather than by serial number.

A device identifier may appear in an authorisation record as *evidence about a capture*. It
must never appear in anything the wallet key depends on.

## Not in Phase 1

Palm image processing, biometric template generation, fuzzy extraction, biometric-to-key
derivation, PAD algorithms, USB protocol work, vendor SDK integration, scanner attestation and
secure-element integration are all out of scope until Phase 1 has been reviewed. USB-C is a
cable; it is a transport and not a security property, and nothing should be shaped around it.
